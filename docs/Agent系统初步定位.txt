# Agent系统初步定位

# 一、总体架构定位

你的系统建议定位为：

```Plain Text
Quant Multi-Agent Trading System
多 Agent 智能量化交易系统
```

核心目标不是让 AI “拍脑袋买卖”，而是让不同 Agent 像一个小型交易机构一样协作：

```Plain Text
数据系统负责提供可靠事实
分析师 Agent 负责多维度分析
研究员 Agent 负责多空辩论与综合判断
交易员 Agent 负责形成交易计划
风控 Agent 负责审核、否决、降仓、熔断
执行系统负责模拟或真实下单
日志/报告系统负责留痕、复盘、评估
```

推荐总原则：

> **AI 负责分析与解释，规则系统负责风控与执行边界，交易执行必须可审计、可回滚、可熔断。**

# 三、核心设计原则

你这个系统要坚持几个原则。

## 1\. 数据事实与 Agent 分析分离

Agent 不应该直接乱抓网页、乱理解原始页面。正确方式是：

```Plain Text
数据采集器 → 数据标准化 → 数据质量校验 → 结构化数据 → Agent使用
```

Agent 拿到的应该是：

```JSON
{
  "symbol": "510300",
  "name": "沪深300ETF",
  "latest_price": 3.982,
  "change_pct": 1.25,
  "ma20": 3.85,
  "ma60": 3.72,
  "volume_ratio": 1.42,
  "position": {
    "quantity": 2000,
    "available_quantity": 1000,
    "cost": 3.80
  },
  "risk": {
    "max_drawdown_20d": -0.052,
    "volatility_20d": 0.018
  }
}
```

不要让 Agent 每次从网页中自行推理字段含义，否则稳定性差。

---

## 2\. AI 不能越过风控

交易链路必须是：

```Plain Text
分析建议 → 交易计划 → 风控审核 → 执行确认 → 下单 → 成交核验 → 日志归档
```

不能是：

```Plain Text
Agent觉得可以买 → 直接下单
```

这非常危险。

---

## 3\. 回测不能一次性把未来数据喂给 Agent

你提到这一点非常关键。正确回测方式是事件驱动：

```Plain Text
T时刻之前的数据 → Agent分析 → 产生信号 → 模拟下单 → 推进到T+1 → 更新账户
```

不能让 Agent 看到未来 K 线。

---

## 4\. 大模型只处理“摘要后的状态”

分时回测如果每 5 分钟都把完整 K 线、新闻、盘口塞给大模型，token 成本会非常高。

更合理的是：

```Plain Text
原始数据 → 脚本计算特征 → 生成市场状态摘要 → Agent分析
```

例如不要喂 300 根 5 分钟 K 线，而是喂：

```Plain Text
过去5分钟涨跌幅：+0.42%
过去30分钟涨跌幅：+1.18%
当前价格高于VWAP：是
量比：1.8
MACD状态：金叉后扩散
盘口买卖差：买盘略强
最近3个事件：无重大公告，板块情绪偏强
```

这样成本和稳定性都更好。

# 五、数据源接入模块

这是系统地基。你说要参考东方财富个股页面包含的信息，这个方向对，但不能只依赖单一来源。

## 1\. 行情数据分类

你需要的数据大概包括：

|数据类型|示例|用途|
|---|---|---|
|日 K 数据|开高低收、成交量、成交额|中低频策略、回测|
|分钟 K 数据|1分钟、5分钟、15分钟、30分钟|短周期回测、盘中监控|
|实时行情|最新价、涨跌幅、成交量|实盘决策|
|盘口数据|买一卖一、五档、十档|交易执行、流动性判断|
|逐笔成交|成交价、成交量、方向|高频/盘口分析，初期可不做|
|ETF 基础信息|代码、名称、规模、费率、跟踪指数|ETF池构建|
|ETF 净值与溢价率|IOPV、净值、折溢价|跨境/商品ETF风险控制|
|财务数据|营收、利润、ROE、PE/PB|股票基本面|
|指数数据|沪深300、中证500、纳指等|市场状态判断|
|板块数据|行业涨跌、资金流|行业轮动|
|资金流数据|主力净流入、北向资金|辅助情绪|
|新闻数据|个股新闻、行业新闻、宏观新闻|事件驱动|
|公告数据|财报、减持、增发、重组|风险过滤|
|舆情数据|股吧、雪球、微博等|情绪分析|
|交易日历|是否交易日、节假日|调度|
|账户数据|资金、持仓、委托、成交|交易闭环|

---

## 2\. 推荐数据源组合

### 免费/低成本初期方案

|数据源|适合内容|说明|
|---|---|---|
|AkShare|A股、ETF、基金、宏观、东方财富数据|适合研究和初期系统|
|Tushare|日线、基础数据、交易日历、财务|比较规范|
|东方财富接口/页面|行情、资金流、公告、股吧|信息丰富，但接口稳定性需封装|
|新浪/腾讯行情|实时行情备用源|可做冗余|
|交易所官网|公告、ETF信息|权威但抓取麻烦|
|券商行情 API|实盘行情|如果用 QMT/PTrade 可接入|

### 中后期更稳方案

|数据类型|推荐|
|---|---|
|日线/财务/交易日历|Tushare Pro / Choice / Wind|
|实时行情|券商行情 API / QMT / PTrade|
|新闻公告|东方财富 \+ 交易所公告 \+ 巨潮资讯|
|舆情|东方财富股吧/雪球/第三方舆情API|
|ETF 净值溢价|基金公司/东方财富/交易所数据|

---

## 3\. 数据源稳定性设计

必须做多源冗余：

```Plain Text
主数据源失败 → 自动切换备用源
主数据源字段异常 → 数据质量校验拦截
数据延迟过大 → 禁止交易
关键行情缺失 → 禁止交易
```

例如行情源设计：

```YAML
market_data_sources:
  daily_bar:
    primary: tushare
    backup:
      - akshare
      - eastmoney
  realtime_quote:
    primary: qmt
    backup:
      - eastmoney
      - sina
  news:
    primary: eastmoney
    backup:
      - cninfo
      - exchange
```

# 六、数据采集与调度模块

这个模块负责定时拉数据。

## 1\. 采集方式

```Plain Text
定时采集：每日收盘后拉日线、公告、财务
盘中轮询：每1分钟/5分钟拉实时行情
事件触发：有新公告、新新闻、新委托回报时触发
手动刷新：管理员触发更新
```

---

## 2\. 调度器建议

可用：

```Plain Text
APScheduler
Celery Beat
Airflow
Prefect
Windows任务计划
Linux cron
```

初期建议：

```Plain Text
APScheduler + SQLite/PostgreSQL
```

简单够用。

---

## 3\. 采集任务示例

```Plain Text
每日 08:30：更新交易日历、ETF池
每日 09:20：盘前新闻与公告扫描
交易时段每 1分钟：更新持仓标的实时行情
交易时段每 5分钟：触发盘中分析任务
每日 15:10：拉取收盘行情
每日 16:00：更新资金流、公告、新闻
每日 17:00：生成日终报告
```

# 七、数据清洗与质量校验模块

这是非常重要但容易被忽略的模块。

## 1\. 校验内容

|校验项|示例|
|---|---|
|缺失值|OHLC 是否为空|
|异常价格|收盘价为 0、涨跌幅超过规则限制|
|时间连续性|分钟K是否缺失|
|复权一致性|股票回测是否使用正确复权|
|交易日一致性|非交易日不应有交易数据|
|多源比对|Tushare 和 AkShare 收盘价偏差过大|
|延迟检测|实时行情时间戳超过阈值|
|成交量异常|成交量为 0 但价格变化明显|
|ETF溢价异常|跨境 ETF 溢价过高需风险提示|

---

## 2\. 数据质量状态

建议每条数据带质量标签：

```Plain Text
VALID
MISSING
DELAYED
SUSPICIOUS
CONFLICT
ESTIMATED
```

Agent 和交易系统只能使用：

```Plain Text
VALID
```

或经过明确允许的：

```Plain Text
ESTIMATED
```

# 八、统一数据服务层

不要让每个 Agent 自己去调用不同 API。

应该有一个统一数据服务：

```Plain Text
MarketDataService
FundamentalDataService
NewsDataService
SentimentDataService
AccountDataService
PositionDataService
OrderDataService
```

## 示例接口

```Python
get_daily_bars(symbol, start_date, end_date)
get_minute_bars(symbol, start_time, end_time, freq="5m")
get_realtime_quote(symbol)
get_order_book(symbol)
get_news(symbol, start_time, end_time)
get_announcements(symbol, start_date, end_date)
get_fundamentals(symbol)
get_account_snapshot()
get_positions()
get_available_quantity(symbol)
```

这样 Agent 只调工具，不关心底层数据源。

# 十一、各 Agent 详细职责

## 1\. 数据管理员 Agent

职责：

```Plain Text
确认数据是否齐全
确认数据是否新鲜
识别缺失和异常数据
决定是否允许进入分析流程
```

输入：

```Plain Text
数据质量报告
行情更新时间
新闻更新时间
账户更新时间
```

输出：

```JSON
{
  "data_status": "PASS",
  "warnings": [],
  "blocked_reason": null
}
```

如果数据不合格，直接中止交易分析。

---

## 2\. 基本面分析师 Agent

更适合股票，对 ETF 可弱化。

职责：

```Plain Text
分析估值水平
分析盈利能力
分析成长性
分析财务风险
识别低估/高估
```

输出示例：

```JSON
{
  "agent": "fundamental_analyst",
  "view": "neutral",
  "score": 62,
  "key_points": [
    "ROE稳定但利润增速放缓",
    "估值位于近三年中位数附近"
  ],
  "risks": [
    "现金流转弱"
  ],
  "confidence": 0.68
}
```

---

## 3\. 技术分析师 Agent

职责：

```Plain Text
分析趋势
判断支撑压力
识别突破/跌破
分析成交量配合
给出技术面评分
```

对于 ETF 这个 Agent 很重要。

输出：

```JSON
{
  "agent": "technical_analyst",
  "view": "bullish",
  "score": 78,
  "signals": [
    "价格站上20日和60日均线",
    "20日动量排名靠前",
    "成交额放大"
  ],
  "invalid_condition": "跌破60日均线",
  "confidence": 0.74
}
```

---

## 4\. 情绪分析师 Agent

职责：

```Plain Text
分析股吧/雪球/新闻评论热度
判断市场情绪偏多/偏空
识别极端情绪
识别拥挤交易
```

注意：情绪数据容易噪声很大，只能辅助，不能主导。

---

## 5\. 新闻公告分析师 Agent

职责：

```Plain Text
提取新闻和公告事件
识别利好/利空/中性
判断事件影响期限
标记重大风险事件
```

输出要结构化：

```JSON
{
  "agent": "news_analyst",
  "event_summary": [
    {
      "type": "announcement",
      "sentiment": "negative",
      "impact": "medium",
      "summary": "公司发布减持公告"
    }
  ],
  "overall_view": "bearish",
  "risk_level": "medium"
}
```

---

## 6\. 宏观与市场环境分析师 Agent

职责：

```Plain Text
判断大盘状态
判断市场风险偏好
分析利率、汇率、海外市场
判断当前适合进攻还是防守
```

ETF 轮动系统中这个很有用。

---

## 7\. ETF 专项分析师 Agent

如果你主做 ETF，建议专门设计这个角色。

职责：

```Plain Text

分析折溢价
分析跟踪指数
分析成交额和规模
分析同类ETF替代关系

```

例如：

```Plain Text

```

---

## 8\. 看多研究员 Agent

职责：

```Plain Text

寻找上涨驱动

```

---

## 9\. 看空研究员 Agent

职责：


这个角色很重要，可以防止 Agent 一味附和。

---

## 10\. 首席研究员 / 投研委员会 Agent

职责：

```Plain Text

```

输出：

```JSON
{
  "research_decision": "BUY_CANDIDATE",
  "confidence": 0.72,
  "expected_holding_period": "5-20 trading days",
  "upside_reason": "...",
  "downside_risk": "...",
  "key_monitoring_points": []
}
```

---

## 11\. 交易员 Agent

职责：

```Plain Text
把研究结论转成交易计划
决定买卖方向
决定目标仓位
决定交易价格类型
决定分批还是一次性
结合账户资金、可用持仓、T+1规则
```

它必须读取：

```Plain Text
当前持仓股数

持仓成本
浮盈浮亏
账户可用资金
证券市值
手续费
最小交易单位

```

输出不是“建议买”，而是完整订单计划：

```JSON

  "symbol": "510300",

  "reason": "技术趋势向上且研究结论支持",
  "fallback": "若价格高于4.02则取消"
}
```

## 12\. 风险管理 Agent

这是最高优先级之一。

职责：

```Plain Text
审核交易计划
计算账户风险
检查单标的仓位
检查行业集中度
检查最大回撤
检查流动性
检查异常行情
决定批准、拒绝、降仓、人工确认
```

# 十二、Agent 框架选型建议

你列了很多框架，我帮你按“量化交易场景”重新评估。

## 1\. 不建议一开始上太复杂框架

量化交易系统的重点不是炫 Agent 框架，而是：

```Plain Text

交易执行安全

```

Agent 框架应该服务这些目标。

---

## 2\. 各框架适配性

|框架|适合度|说明|
|---|---|---|
|LangGraph|很推荐|适合有状态、多节点、可控流程，适合交易决策工作流|
|LangChain|推荐|工具生态丰富，适合作为基础工具层|
|LlamaIndex|推荐|适合新闻、公告、研报、知识库 RAG|
|AutoGen|可选|多 Agent 对话强，但生产控制要加强|
|CrewAI|可用于原型|快速搭角色，但复杂流程控制一般|
|PydanticAI|推荐|类型安全、结构化输出，适合交易系统|
|Semantic Kernel|企业集成可选|\.NET/企业系统友好|
|Langflow|学习/原型|可视化适合入门，不建议直接做核心生产|
|OpenAI SDK|推荐|简单直接，适合自研编排|
|ReAct|适合作为单 Agent 工具调用模式|但交易系统不能完全自由 ReAct|

## 3\. 我的推荐组合

### MVP 阶段


# 十四、回测系统设计

你第 5 点非常关键。回测系统要单独重点设计。

## 1\. 回测模式

建议支持三种模式：

```Plain Text
日线回测模式
分钟回测模式
事件驱动回测模式
```

---

## 2\. 日线回测

适合：

```Plain Text
ETF轮动
中低频趋势策略
月度/周度调仓
```

流程：

```Plain Text
T日收盘后获取数据
Agent基于T日及之前数据分析
生成T+1交易计划
T+1开盘价/成交均价模拟成交
更新账户
```

---

## 3\. 分钟回测

你说的 5 分钟增量喂数据是对的。

流程：

```Plain Text
09:30 数据窗口初始化
09:35 喂入09:30-09:35新增数据
Agent/策略引擎判断
模拟订单撮合
09:40 喂入09:35-09:40新增数据
继续推进
...
15:00 收盘结算
```

重点：

```Plain Text
每次只能看到当前时间点之前的数据
不能看到未来K线
新闻公告也要按发布时间进入系统
账户状态也要逐步更新
```

---

## 4\. 回测时不要每一步都调用大模型

否则成本会爆炸，而且回测速度极慢。

建议分层：

### 高频部分由规则/脚本跑

```Plain Text
技术指标计算
止损止盈判断
成交撮合
账户更新
风控硬规则
```

### Agent 只在关键节点调用

```Plain Text
开盘前
重大信号触发
新闻公告出现
仓位变动前
收盘复盘
```

例如：

```YAML
agent_call_policy:
  intraday:
    normal_interval: 30min
    urgent_triggers:
      - price_change_gt_2pct
      - volume_ratio_gt_2
      - stop_loss_near
      - major_news
      - risk_limit_triggered
```

这样既符合真实流程，又能控制 token。

---

## 5\. 回测数据精度要求

需要存：

```Plain Text
历史日K
历史分钟K
历史复权因子
历史公告发布时间
历史新闻发布时间
历史指数数据
历史资金流，如果能拿到
历史成分股，如果做指数/行业
```

对于股票，要注意：

```Plain Text
前复权/后复权/不复权
停牌
涨跌停
除权除息
新股上市
ST变更
```

对于 ETF，要注意：

```Plain Text
分红
份额变化
折溢价
流动性变化
跟踪指数历史
```

---

## 6\. 回测撮合模型

不能简单认为一定按收盘价成交。

至少支持：

```Plain Text
下一根K线开盘价成交

市价单按滑点成交
成交量限制
涨跌停无法成交
盘口价差模拟

```

初期可以这样：

```Plain Text

分钟回测：下一分钟开盘价或VWAP + 0.05%滑点
```

## 7\. 回测指标

必须输出：


# 十六、实盘交易系统设计

这是财产安全核心，必须重点处理。

## 1\. 推荐实盘接入方式

优先级建议：

```Plain Text
1. 券商官方量化接口
2. QMT / MiniQMT
3. PTrade
4. 其他正规交易API
5. 模拟点击客户端：不推荐
```

---

## 2\. 实盘系统分层

```Plain Text
交易信号层
  ↓
交易计划层
  ↓
风控审核层
  ↓
人工确认层，可配置
  ↓
订单执行层
  ↓
订单状态监控层
  ↓
成交核验层
  ↓
账户同步层
  ↓
审计日志层
```

---

## 3\. 下单前检查

实盘每一笔订单前必须检查：

```Plain Text
是否交易日
是否交易时间
标的是否可交易
是否停牌
是否涨跌停
行情是否新鲜
账户是否登录
资金是否足够
持仓是否足够
可用股数是否足够
订单数量是否符合最小单位
单笔金额是否超限
单日交易金额是否超限
单日交易次数是否超限
是否重复下单
是否存在未完成同方向订单
是否触发风控熔断
是否需要人工确认
```

---

## 4\. 多重确认机制

建议分级：

```Plain Text
低风险：自动执行
中风险：邮件/界面确认后执行
高风险：禁止执行
异常风险：熔断全部交易
```

示例：

```YAML
confirmation_policy:
  auto_execute:
    max_order_amount: 1000
    risk_level: low
  require_email_confirm:
    max_order_amount: 5000
    risk_level: medium
  block:
    risk_level: high
```

不过邮件确认要注意延迟，不适合高频，只适合低频/半自动。

---

## 5\. 订单执行失败处理

需要定义状态机。

```Plain Text
CREATED
RISK_CHECKED
SUBMITTED
ACCEPTED
PARTIALLY_FILLED
FILLED
CANCEL_PENDING
CANCELLED
REJECTED
FAILED
UNKNOWN
```

失败处理：

|场景|处理|
|---|---|
|下单接口失败|查询账户和委托，确认是否实际提交|
|返回未知状态|不重复下单，先查询订单|
|资金不足|重新计算数量或放弃|
|价格超限|调整价格或取消|
|部分成交|剩余部分继续等待/撤单|
|长时间未成交|撤单或改价，必须重新风控|
|撤单失败|查询订单状态，禁止重复操作|
|网络中断|暂停交易，人工介入|
|账户状态异常|熔断交易|

---

## 6\. 防重复下单机制

非常重要。

每个交易计划生成唯一 ID：

```Plain Text
decision_id
risk_check_id
order_intent_id
broker_order_id
```

同一个 `order_intent_id` 只能提交一次。

即使 API 超时，也不能立刻重复下单，必须先查询：

```Plain Text
是否已有相同symbol、side、quantity、price、strategy_id的订单
```

---

## 7\. 实盘熔断机制

必须有：

```Plain Text
单日亏损超过X%：停止交易
账户回撤超过X%：停止交易
连续失败订单超过N次：停止交易
行情延迟超过N秒：停止交易
账户同步失败：停止交易
数据源冲突：停止交易
模型输出异常：停止交易
风控服务不可用：停止交易
```

---

## 8\. 人工紧急按钮

必须有：

```Plain Text
一键暂停所有交易
一键取消未成交委托
一键切换只读模式
一键切换模拟盘
一键发送账户快照
```

# 二十八、重点风险提醒

你这个系统最危险的地方不是 Agent 不够聪明，而是：

```Plain Text
数据错误但系统相信了
模型输出不稳定
回测有未来函数
实盘重复下单
订单状态未知时重复提交
风控服务挂了仍然下单
行情延迟还继续交易
账户同步失败
邮件确认链路延迟
Prompt修改后没有回测验证
```

所以实盘前必须保证：

```Plain Text
宁可错过交易，也不能错误交易。
宁可少赚，也不能失控。
任何不确定状态，默认不交易。
```

# 三十、我建议你第一版就这么定

如果要马上落地，我建议第一版目标定为：

```Plain Text
ETF多Agent模拟交易系统 V1
```

范围：

```Plain Text
数据：ETF日K、实时行情、新闻公告、账户模拟数据
周期：日线 + 盘中5分钟监控
Agent：技术、新闻、ETF、看多、看空、交易员、风控、复盘
交易：只做模拟盘
风控：强制硬规则
报告：邮件发送
日志：全链路记录
实盘：暂不自动下单，只预留BrokerAdapter接口
```

这样最稳，不会一开始就把实盘风险打开。
